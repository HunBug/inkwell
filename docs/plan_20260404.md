# Inkwell — Master Plan
**Created:** 2026-04-04  
**Audience:** Owner or an LLM picking up this project cold.

---

## 1. What this project is

A private digitisation project. The owner has **8 handwritten Hungarian personal diaries** written by a teenager/young adult (estimated 1980s–1990s). The handwriting is personal cursive, idiosyncratic, and includes Hungarian diacritics (á, é, í, ó, ö, ő, ú, ü, ű). There are also dyslexic spelling patterns and unconventional orthography throughout.

The goal is a machine-readable transcript of the full collection. The system built to do this is called **Inkwell**.

## 3. The Inkwell system

**Stack:** Python · Flask web UI · SQLite (`working/inkwell.db`) · GPU worker via shared folder (NFS/rsync) · HuggingFace Transformers

**Key directories:**
```
inkwell/              Main Python package
  pipeline/           ingest → preprocess → segment → OCR stages
  web/                Flask app + routes + templates
scripts/              All runnable scripts
working/inkwell.db    SQLite DB (single source of truth)
working/shared/       Shared folder between dev machine and GPU server (NFS mount or rsync)
  jobs/               Finetune / eval / infer_pool job queue
  datasets/           Exported GT datasets (train/val/test JSONL + crops)
  suggestions/        Active learning suggestion files
automation.toml       Main config (GPU host, dataset ID, job params, text policy)
docs/runbook.md       Operational command reference (always current)
```

**Web UI routes:**
- `/annotate` — queue-mode annotation, shows OCR suggestions from latest model predictions
- `/annotate/review`, `/annotate/edit/<line_id>` — review and edit individual annotations
- `/annotate/segment-tuning` — segmentation parameter tuning UI (exists, partial)
- `/jobs` — automation control (export → train → eval), code sync, pool inference, suggestion generation
- `/jobs/results` — experiment + eval CER table by dataset/model/split
- `/jobs/<id>/eval-detail` — per-line CER viewer with crop image, reference, and prediction

**GPU:** Remote server with RTX 2060 (6 GB VRAM). Code is synced via `scripts/sync_code_to_gpu.py`.

## 4. The pipeline stages

```
source scan
    │
    ▼
[preprocess.py]  rotate (90/180/270) → deskew (Hough-line, up to 10°) → split double pages
    │
    ▼
[segment.py]     horizontal projection profile → line bboxes → crop JPEG images
    │
    ▼
[ocr.py]         TrOCR inference → stores OCR_AUTO transcription in DB
    │
    ▼
[annotate UI]    human reviews/corrects → stores HUMAN_CORRECTED transcription
    │
    ▼
[export_gt.py]   → train/val/test JSONL datasets
    │
    ▼
[finetune_trocr.py]  → fine-tuned checkpoint
```

**Non-negotiables:**
1. `line_id` is permanent — existing annotated lines must never be remapped or lost.
2. Re-segmentation must only affect unannotated lines, or must warn before touching annotated ones.
3. Immutable `HUMAN_CORRECTED` transcriptions must never be silently overwritten.
4. Evaluation splits are frozen; do not reshuffle them.
5. Full-pool inference output stays file-based (do not bulk-write ~15k rows into DB per run).

## 6. Why the model has plateaued

`trocr-base-handwritten` was pretrained on the IAM English handwriting corpus. Its decoder has a deep **English language prior**. When it cannot confidently read a Hungarian word, it outputs English-looking sequences that match the stroke shapes visually — it does not produce phonetic noise.

Examples from actual predictions:

| Reference (Hungarian) | Model prediction |
|----------------------|-----------------|
| garázsba néhány könyvért | garisella winding to request |
| az Ákosos fényképtekecset. | an Advisory Employment Assessment . |
| tudok 1 napnál továb | inside I reapplut trouble . |

This is **not** a data quantity problem. 692 samples cannot override millions of English pretraining tokens. More capacity (`trocr-large`) made it worse. Removing the language prior (`trocr-base-stage1`, CER 0.6444) also worsened overall quality, though it eliminated English hallucinations.

## 8. Primary strategy: full manual transcription

The primary plan is to transcribe the diaries manually through the `/annotate` UI at queue mode. This is treated as an enjoyable reading project, not just a data task.

- Already done: ~1,035 lines (~6.5% of corpus)
- Remaining: ~14,962 lines
- Estimated pace: ~25–35 lines/minute for familiar passages → **~65–80 hours total**
- At 5 hours/week: ~3–4 months

The 1,035 existing annotations are permanent evaluation ground truth regardless of what model strategy is used.

## 9. Engineering work plan (parallel to transcription)

Three tracks, ordered by priority. None of them block transcription — they run in parallel.

---

### Track A: Page-level corrections UI

**Problem:** Some double-page scans were split at the wrong horizontal position. Some pages have residual rotation that `deskew_image()` either missed (too few Hough lines) or overcorrected. These page-level errors cascade: every line crop on that page is bad.

**What exists:**
- `preprocess.py` → `deskew_image()`: Hough-line deskew, up to 10°. Skipped if fewer than 8 lines detected or angle std is high.
- `preprocess.py` → `split_double_page()`: searches for the gutter within ±20% of horizontal center. Falls back to exact center if confidence is low.
- DB schema: `source_images` has `orientation_confirmed` (multiples of 90°) but **no column for fine rotation correction or split override**.

**Plan:**

1. Add two columns to `source_images`:
   - `rotation_correction_deg REAL` — fine correction in degrees (applied after the coarse 90° rotation and deskew)
   - `split_x_override INTEGER` — absolute pixel x-position for the split (overrides auto-detection)

2. New web route: `/annotate/fix-page/<source_image_id>`
   - Shows the original double-page scan (or single scan)
   - For DOUBLE images: a draggable vertical split line over the original scan
   - A rotation slider (−10° to +10°, 0.5° steps)
   - Save button → writes to DB
   - Re-preprocess button → triggers re-preprocessing of that one source image (deletes + recreates derived page images + segmentation), with a **guard**: if any annotated lines exist on those pages, shows a warning and requires explicit confirmation

3. `preprocess.py` updated to read `rotation_correction_deg` and `split_x_override` and apply them.

4. A listing page (`/annotate/fix-page`) showing all source images with thumbnails, so you can browse and identify bad ones.

**Scope:** New route file + template + 2 DB columns + small change to `preprocess.py`. Does not touch existing annotated line IDs.

---

### Track B: Line segmentation quality

**Problem:** The horizontal projection segmenter has a known accent/descender conflict:
- `margin_top=24, margin_bottom=19` (hardcoded in `segment.py`) — increased to reduce accent clipping
- On dense pages, the bottom margin of one crop overlaps with the top of the next crop, causing descenders (g, y, p, q) and commas from line N to appear in the crop of the diacritics (á, é, ő) from line N+1
- Merged lines (two lines becoming one crop) are rare

**What exists:**
- `UNUSABLE_SEGMENTATION` flag in transcriptions — already used in the annotation UI to mark bad crops
- Segment tuning table (`segmentation_tuning_configs`) and route `/annotate/segment-tuning` — partially built
- `scripts/recrop_lines.py` — safe re-crop with ID preservation

**Plan:**

1. **Do not strip Hungarian diacritics from GT.** That would permanently corrupt the ground truth. The correct approach is better crops.

2. **Smarter dynamic margin:** Instead of fixed `margin_bottom`, detect the gap between the current line's bottom and the next line's top. If the gap is narrow (< threshold pixels), reduce `margin_bottom` proportionally. This avoids the bleeding artifact on dense pages while keeping the full margin on well-spaced pages.

3. **Targeted re-crop of flagged lines:** Use the `UNUSABLE_SEGMENTATION` flag inventory as the work list. Run `recrop_lines.py` on those lines with adjusted parameters. Annotated lines untouched by default.

4. The existing warning flag in the annotation UI is the right tool — keep it. When you see a bad crop during transcription, flag it and move on; fix it in a batch recrop pass.

**Scope:** Modify `segment_lines_cv_projection()` in `segment.py` (the dynamic margin logic, ~15 lines). `recrop_lines.py` already handles safe re-crop.

### Track C: Hungarian synthetic pre-training data

**Goal:** Inject Hungarian vocabulary into the TrOCR decoder so it stops hallucinating English words. The target is a checkpoint pretrained on Hungarian text before fine-tuning on the real diary annotations.

**Key insight:** The goal is not to simulate the exact handwriting. The decoder learns character n-gram distributions and vocabulary. Rendering Hungarian text in any font (with augmentation) is enough to override the English prior. Dyslexic spelling does not matter at this stage.

**Approach:**

#### Phase 1: Data acquisition
- Download a large Hungarian text corpus (~50–100k sentences):
  - Best option: **CC-100 Hungarian** subset (Common Crawl filtered for Hungarian, available on HuggingFace Datasets)
  - Fallback: Hungarian Wikipedia dump, Project Gutenberg Hungarian books
- Target: 50k–100k sentence fragments of 5–15 words each (matching typical line length)

#### Phase 2: Synthetic image rendering
- Tool: `trdg` (TextRecognitionDataGenerator) — renders text as handwriting-style JPEG crops
- Use 4–6 fonts with handwriting character (e.g. from Google Fonts: Caveat, Patrick Hand, Segoe Script equivalents)
- Augmentation: slight rotation (±3°), Gaussian blur (σ 0.5–1.5), brightness jitter, mild noise
- Output: JPEG crops + corresponding text labels in JSONL format (same schema as existing GT datasets)
- Estimated image count to start: **20k** (feasible render time on CPU, manageable training time on RTX 2060)

#### Phase 3: Pre-fine-tune
- Fine-tune `microsoft/trocr-base-handwritten` on the 20k synthetic Hungarian images
- This produces a checkpoint with a Hungarian-biased decoder
- Use same `finetune_trocr.py` script (just point it at the synthetic dataset)
- Estimated time on RTX 2060: ~2–4 hours for 20k samples × 2–3 epochs

#### Phase 4: Domain fine-tune
- Fine-tune the Phase 3 checkpoint on the 1,035 real diary annotations (train split only)
- Evaluate against frozen val set
- Compare CER to the current best (0.5805k from Round 4 with the English-prior base)

#### Phase 5: Iterate
- If CER improves significantly: increase synthetic data to 50k–100k and repeat
- If no improvement: try rendering Hungarian text in a more handwriting-like style, or investigate whether a non-TrOCR approach (e.g. fine-tuning a vision-language model like PaliGemma or Florence-2) is more tractable

**Scripts to write:**
- `scripts/generate_synthetic_hu.py` — renders Hungarian text corpus to JPEG crops using `trdg` or Pillow directly, outputs JSONL
- No changes to existing pipeline needed; synthetic datasets slot into the same `finetune_trocr.py` flow

**Constraint:** RTX 2060 (6 GB VRAM). Base-sized TrOCR fine-tuning fits. Anything larger does not. Rendering is CPU-side and can run overnight.
